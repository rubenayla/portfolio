## 2026-06-07 — Renaming the Pages repo took the live apex (rubenayla.xyz) down
**What:** During the portfolio/notes split I renamed this repo `ruben → portfolio` via `gh repo rename`. The apex `rubenayla.xyz` (months-stable, Cloudflare-proxied custom domain) stopped loading. `gh api repos/rubenayla/portfolio/pages` showed `https_certificate.state = null`: the rename made GitHub re-evaluate the custom domain and reset/re-issue the cert, but the apex was **proxied (orange cloud)**, so Cloudflare intercepted the Let's Encrypt ACME challenge and re-issuance failed. With no valid origin cert (and Cloudflare on Full-strict), the TLS handshake broke → site down.
**Root cause:** Treated a repo rename as cosmetic. For a GitHub Pages repo with a **proxied** custom domain, a rename triggers a cert re-issue that the proxy blocks — same fragility that makes proxied Pages break on every Let's Encrypt renewal (~60 days).
**Prevention:**
- Before renaming a Pages repo with a custom domain, set that domain to **DNS only (grey cloud)** in Cloudflare first, so the post-rename cert re-issue can complete. Re-check `gh api repos/<o>/<r>/pages -q .https_certificate.state` after.
- Recovery (also the steady-state recommendation): keep Pages custom-domain records grey/DNS-only. To fix a stuck cert, grey-cloud → force re-verify by removing + re-adding the cname via the Pages API → poll until `approved` → set `https_enforced=true`. Full detail in `~/repos/notes/.agents/history.md` (2026-06-07 DNS-only gotcha).

## 2026-07-02 — Inlining the journey 404'd its videos (raw HTML `<source>` paths not rewritten)
**What:** After including `build-journey/index.md` into the kart overview via `pymdownx.snippets`, the three journey videos (`battery-spot-weld`, `first-manual-drive`, `planetary-cad`) showed an empty player on `/projects/kart/`. They used `<source src="../videos/x.mp4">`, which is correct at `/build-journey/` (one level deep) but resolves to `/projects/videos/x.mp4` (404) when the same content renders at `/projects/kart/` (two levels deep).
**Root cause:** MkDocs rewrites relative paths only in **markdown** syntax (`![](../images/…)`), per output page — which is why the journey's 19 markdown images survived the include (and why `projects/` and `build-journey/` being the same depth masked the issue for images). It does **not** rewrite paths inside **raw HTML**, so `<source src>` stayed literal. Once the journey is hosted at two different URL depths, no single relative `../` path can satisfy both. I verified images rendered and declared the include done without checking the HTML-embedded videos.
**Prevention:**
- **When content is included/rendered at more than one URL depth, raw-HTML asset paths (`<source>`, `<img src>`, `<a href>` written as HTML) must be root-absolute (`/videos/…`)**, not relative. Safe here because the site is served from the apex root (`site_url: https://rubenayla.xyz/`). Markdown-syntax assets are fine relative — MkDocs rewrites them.
- **Grep every `<source`/`<video`/`<img`/`.mp4` in included content after wiring up a `snippets` include**, and load the host page (not just the source page) to confirm media plays. Same "grep all instances" rule as the prior video-path bugs — this is the third time a kart video path has broken.
