**What:** `mkdocs serve` adds `/portfolio/` prefix based on `site_url`, causing 404s on localhost.
**Root cause:** MkDocs serve uses site_url to compute paths.

## 2026-06-30 — Fabricated a cropped still instead of using the video the user published
**What:** Migrating the 2026-06-29 planetary-reducer LinkedIn post into the Build Journey, I cropped a frame out of a full Fusion 360 screenshot, cleaned the UI chrome out of the crop, and embedded that as the post's image. The user objected: *"why this image? i didnt share that. it was a cool video."* The published media for that post was the video `01_planetary_v22_cad_2x.mp4` — named explicitly in the folder's `README.md` ("Format: short video … 01_planetary_v22_cad_2x.mp4"). I had to delete the fabricated still and embed the real video.
**Root cause:** A chain of three: (1) I trusted a wrong line in AGENTS.md ("demo videos go on YouTube") and ruled out self-hosting the video before looking at the assets; (2) with the video off the table, the post "needed an image," so I doctored a screenshot to make it presentable — optimizing for *looks clean* over *is what the user published*; (3) when the user corrected the YouTube premise, I self-hosted the other posts' videos but never revisited the planetary crop — a decision whose justification had already died. Underneath all of it: I read the folder's `post.md` but not its `README.md`, which named the exact media in one line.
**Prevention:**
- **Never fabricate, crop, recolor, or synthesize a media asset to stand in for one the user actually published.** This is the validated-only rule (memory `feedback_validated_videos`): Build-Journey media comes from the published post folder's actual files, not a frame you extracted and tidied. If the only clean-looking option is one you'd have to manufacture, that's the signal you're using the wrong asset.
- **Read the post folder's `README.md` before choosing media** — it states the published `Format` and names the exact file(s). `post.md` is the body text; `README.md` is the media/format source of truth.
- **When a premise is corrected, re-derive every decision that premise caused** — not just the one in front of you. A workaround loses its justification the moment its premise dies; grep the diff for other choices the dead premise produced.

## 2026-06-07 — Renaming the Pages repo took the live apex (rubenayla.xyz) down
**What:** During the portfolio/notes split I renamed this repo `ruben → portfolio` via `gh repo rename`. The apex `rubenayla.xyz` (months-stable, Cloudflare-proxied custom domain) stopped loading. `gh api repos/rubenayla/portfolio/pages` showed `https_certificate.state = null`: the rename made GitHub re-evaluate the custom domain and reset/re-issue the cert, but the apex was **proxied (orange cloud)**, so Cloudflare intercepted the Let's Encrypt ACME challenge and re-issuance failed. With no valid origin cert (and Cloudflare on Full-strict), the TLS handshake broke → site down.
**Root cause:** Treated a repo rename as cosmetic. For a GitHub Pages repo with a **proxied** custom domain, a rename triggers a cert re-issue that the proxy blocks — same fragility that makes proxied Pages break on every Let's Encrypt renewal (~60 days).
**Prevention:**
- Before renaming a Pages repo with a custom domain, set that domain to **DNS only (grey cloud)** in Cloudflare first, so the post-rename cert re-issue can complete. Re-check `gh api repos/<o>/<r>/pages -q .https_certificate.state` after.
- Recovery (also the steady-state recommendation): keep Pages custom-domain records grey/DNS-only. To fix a stuck cert, grey-cloud → force re-verify by removing + re-adding the cname via the Pages API → poll until `approved` → set `https_enforced=true`. Full detail in `~/repos/notes/.agents/history.md` (2026-06-07 DNS-only gotcha).
